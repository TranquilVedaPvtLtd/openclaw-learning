OpenClaw Architecture

A complete professor-level guide to every component, flow, and design decision in OpenClaw — the open-source personal AI assistant platform.

Imagine you have a really smart assistant (like Jarvis from Iron Man). But this assistant lives inside your computer, not a movie. OpenClaw is the entire infrastructure that makes this possible. It connects your assistant to WhatsApp, Telegram, Slack, and 20+ other apps, gives it the ability to control a web browser, take photos from your phone, schedule tasks, and remember your conversations. Think of it as the "nervous system" — the AI model (Claude, GPT) is the brain, but OpenClaw is everything else: the ears (messaging channels), the mouth (reply delivery), the hands (tools), the memory (sessions), and the clock (cron jobs).

OpenClaw is a local-first, multi-channel AI gateway built in TypeScript (Node >= 22). It provides a WebSocket-based control plane (the Gateway) that manages agent sessions, routes messages across 23+ messaging platforms via a plugin architecture, executes tools (shell, browser, canvas, devices), schedules automation (cron, webhooks, heartbeats), and coordinates companion device nodes (macOS, iOS, Android). The codebase compiles to 625 JavaScript modules, supports 44 extensions (channel/capability plugins), ships with 52 built-in skills, and exposes a typed Plugin SDK for custom integrations. It embeds the pi-mono agent runtime for LLM orchestration with tool streaming.

OpenClaw System Architecture

Layer 1: CLI Entry Point

When you type openclaw in your terminal, this is where everything begins. It's like turning the ignition key in a car. The CLI checks your Node.js version, loads the compiled code, and routes your command (like gateway, agent, channels) to the right handler. It's the remote control for the entire system.

The entry point is openclaw.mjs — a thin ESM loader that verifies Node >= 22.12, enables V8 compile cache, installs a process warning filter, then dynamic-imports dist/entry.js. The entry module initializes the CLI program via program.js and program-context.js, which uses a command registry (command-registry.js) pattern. Each CLI subcommand (gateway, agent, channels, cron, models, skills, config, doctor, etc.) is a separate module under register.*.js:

  • register.agent.js — agent turns
  • register.message.js — send/poll messages
  • register.status-health-sessions.js — health/status/sessions
  • register.onboard.js — wizard
  • register.configure.js — interactive config
  • register.maintenance.js — doctor, update, cleanup
  • register.setup.js — initial setup
  • register.subclis.js — gateway-cli, channels-cli, cron-cli, models-cli, skills-cli, browser-cli, nodes-cli, devices-cli, webhooks-cli, security-cli, etc.

Layer 2: The Gateway (WebSocket Control Plane)

The Gateway is the airport control tower of OpenClaw. Every message from every app (WhatsApp, Telegram, Slack, etc.) lands at the Gateway. Every response goes out through the Gateway. Every tool the AI wants to use gets dispatched by the Gateway. Every scheduled task gets triggered by the Gateway. It runs as a background service on your computer, always on, always listening. It communicates via WebSockets (a persistent two-way connection, like a phone call that stays open) on a single port (default: 18789).

The Gateway is a single-process WebSocket + HTTP server bound to 127.0.0.1:18789 by default. Key architectural properties:

  • Single WS port — all clients (channels, CLI, macOS app, iOS/Android nodes, WebChat) connect to the same port. Protocol is typed JSON over WS.
  • Hot reload — config changes to openclaw.json are detected and applied without restart. Mode can be watch (file watcher), poll (periodic), or hybrid.
  • Auth — token-based (Bearer) or password-based. Tailscale identity headers supported when exposed via Tailscale Serve.
  • Supervision — can install as launchd (macOS) or systemd (Linux) user service via openclaw gateway install.
  • RPC protocol — all operations (sessions, config, cron, pairing) exposed as typed RPC methods over WebSocket.
  • Invariants: Gateway is source of truth for session state; sessions never travel over the wire; tool exec happens on the Gateway host (device actions via node.invoke).

Layer 3: Agent Runtime (Pi)

The Agent Runtime is the thinking engine. When a message arrives, the Gateway wakes up the agent, which is like a brain that can read, think, and act. The "Pi" runtime is the engine that talks to the AI model (like Claude or GPT), sends it your message along with all the context (who you are, what tools are available, what you talked about before), receives the AI's response, and if the AI wants to do something (run a command, send a message, open a browser), the runtime executes those tool calls and feeds the results back to the AI until it's done thinking.

OpenClaw embeds pi-mono as its agent runtime — a lightweight, single-process LLM orchestration engine that runs in RPC mode within the Gateway process. Key components:

  • Workspace contract — each agent has a workspace directory containing identity files (SOUL.md, IDENTITY.md, USER.md, AGENTS.md, TOOLS.md, HEARTBEAT.md) that are injected into the system prompt.
  • Prompt assembly — system prompt is constructed from: workspace files + matched skills + session history + model-specific formatting.
  • Tool streaming — tool calls are streamed as they're generated (not batched), allowing parallel execution.
  • Block streaming — response text is streamed in blocks for real-time delivery to channels with human-like pacing.
  • Compaction — when context grows too large, automatic summarization compresses older turns while preserving key information.
  • Sub-agents — can spawn isolated sub-agent sessions for parallel work, with configurable model, concurrency limits, and archive policies.

Layer 4: Session Management

Sessions are the agent's memory for each conversation. When you chat with the assistant on WhatsApp, it remembers what you said earlier because each conversation is saved as a "session." Different people get different sessions. Different channels (WhatsApp vs Telegram) get different sessions. Sessions can automatically reset daily (like wiping the whiteboard every morning) or after being idle too long. When a session gets too large, it gets "compacted" — the older parts are summarized to save space while keeping the important context.

Sessions are stored as JSONL files (append-only, one JSON object per line) in agents/<id>/sessions/. Key design decisions:

  • Session key derivation — configurable via dmScope: main (single global), per-peer (per user), per-channel-peer (per user per channel), per-account-channel-peer (most granular).
  • Identity links — can merge sessions across channels for the same person (e.g., same user on Telegram + Discord).
  • Gateway is source of truth — sessions never travel over the wire; the Gateway maintains all state.
  • Reset policies — daily (at specific hour), idle (after N minutes), per-chat-type overrides (resetByType).
  • Maintenance — pruneAfter, maxEntries, rotateBytes for automatic cleanup.
  • Compaction — when context approaches model limits, older turns are summarized. Tool results get pruned (large outputs replaced with summaries). Soft pruning (trim tool results) → hard pruning (remove entire turns) hierarchy.
  • Send policies — rules can deny outbound messages based on channel, chat type, or session key prefix.
  • Queue modes — steer (new message replaces current), followup (appends to current run), collect (batches messages), steer-backlog (queues for sequential processing).

Layer 5: Model & Auth Layer

OpenClaw isn't locked to one AI brain — it can use many. You can use Claude (Anthropic), GPT (OpenAI), Gemini (Google), or even run local models on your own hardware. The auth layer manages API keys, OAuth tokens, and subscription credentials. If one provider goes down or you hit a rate limit, it automatically falls back to the next one. Think of it like having multiple phone plans — if one network drops, you seamlessly switch to another.

  • Auth profiles — stored in credentials/auth-profiles.json. Each profile has: provider, mode (token/oauth), credentials, cooldown state. Profile IDs like anthropic:manual, openai:copilot-proxy.
  • Rotation — profiles for the same provider are tried in order. On failure (401/403/429), the profile enters cooldown and next is tried.
  • Session stickiness — once a session starts with a model, it stays on that model unless explicitly switched (prevents context format mismatch).
  • Model fallbacks — if the primary model fails, fallback models are tried: agents.defaults.model.fallbacks: ["openai/gpt-5.2"].
  • Billing disable — if billing is suspended, the profile is marked disabled and skipped.
  • Model aliases — shortcuts like opus → anthropic/claude-opus-4-6.
  • Supported providers: Anthropic (direct + OAuth), OpenAI (direct + Copilot proxy + Codex OAuth), Google (Gemini CLI auth), Ollama, vLLM, sglang, MiniMax, Qwen, and any OpenAI-compatible endpoint.

Layer 6: Channel System (23+ Messaging Platforms)

Channels are the ears and mouth of OpenClaw. Each channel is a persistent connection to a messaging platform. When someone sends you a WhatsApp message, the WhatsApp channel plugin receives it, translates it into a standard format, and hands it to the Gateway. When the AI responds, the reply goes back through the channel plugin and gets translated into WhatsApp format. Each channel handles its own quirks — WhatsApp uses QR code login, Telegram uses bot tokens, Discord uses bot tokens + slash commands, Slack uses Bolt SDK, etc.

The channel system is implemented as an extension/plugin architecture:

  • Plugin SDK — each channel imports from openclaw/plugin-sdk (or channel-specific SDKs like openclaw/plugin-sdk/whatsapp).
  • Extension lifecycle — loaded by plugin-registry.js, initialized with config, maintains persistent connections.
  • Message normalization — all inbound messages are converted to a standard envelope: sender, channel, chatType (dm/group), text, media, metadata.
  • Outbound delivery — outbound.js → deliver-runtime.js → channel-specific deps-send-*.runtime.js.
  • Delivery queue — failed sends are persisted to delivery-queue/*.json for retry.
  • Streaming/chunking — long responses are chunked per channel limits. Preview streaming (edit-in-place) on Telegram/Discord/Slack. Human-like pacing.
  • Access control per channel: dmPolicy (pairing/allowlist/open/disabled), allowFrom lists, groupPolicy, requireMention for groups.
  • Acknowledgment reactions — agent can react to messages (thinking/done emojis) on supported channels.

Layer 7: Tools & Execution

Tools are the agent's hands. When the AI decides it needs to do something — run a terminal command, read a file, open a website, send a message, create a cron job — it issues a "tool call." The Gateway intercepts this, executes the action on your computer, and returns the result to the AI. There's a safety layer: some tools are marked "dangerous" and require extra confirmation or are restricted in sandboxed sessions.

Layer 8: Skills Platform

Skills are instruction manuals that teach the agent new abilities. Each skill is a folder with a SKILL.md file that says "here's how to use this tool." For example, the "weather" skill teaches the agent how to check the weather. The "github" skill teaches it to use the GitHub CLI. Skills can include scripts, templates, and reference docs. There are three levels: built-in (shipped with OpenClaw), managed (installed from ClawHub marketplace), and workspace (custom, per-agent).

  • Skill format — AgentSkills-compatible folder with SKILL.md (frontmatter: name, description, user-invocable, gating). Optional: scripts/, references/, assets/.
  • Three locations: Bundled ($(npm root -g)/openclaw/skills/), Managed (ClawHub-installed), Workspace (workspace-*/skills/).
  • Precedence: workspace > managed > bundled (allows overriding built-in skills).
  • Gating — skills declare requirements (binaries, env vars, config keys, platform). Only eligible skills are loaded.
  • Config injection — skills can receive per-skill config and env vars from skills.entries.<name> in openclaw.json.
  • Session snapshot — <skill_dir> placeholder in SKILL.md expands to the actual skill path at runtime.
  • Skills watcher — file changes to skills directories trigger hot-reload with configurable debounce.
  • Token impact — each loaded skill adds to the system prompt size. OpenClaw tracks and reports skill token usage.

Layer 9: Automation (Cron, Webhooks, Heartbeats)

Automation is the alarm clock and doorbell of OpenClaw. Cron jobs wake the agent at scheduled times (like a 6 AM morning briefing every day). Webhooks let external services ring the doorbell (like Gmail sending a notification when you get an email). Heartbeats are gentle periodic check-ins (the agent wakes up every 30 minutes to check if anything needs attention). Together, these make the agent proactive, not just reactive.

Layer 10: Browser Control

OpenClaw gives the AI its own web browser. It's not your browser — it's a separate, isolated Chrome profile (with a distinctive orange border so you know which is the agent's). The agent can navigate to websites, fill out forms, click buttons, take screenshots, download files, and interact with web apps. This is how the agent can do things like check a website, fill out a form for you, or take screenshots of a dashboard. It uses Chrome DevTools Protocol (CDP) — the same technology Chrome's developer tools use.

  • Isolation — dedicated browser profile (openclaw) with separate cookies, history, extensions. CDP port 18800 by default.
  • Multi-profile — can configure multiple profiles (openclaw, work, remote) with different CDP ports and colors.
  • Browsers supported — Chrome, Brave, Edge, Chromium. Configurable executablePath.
  • Snapshot system — AI-optimized DOM snapshots with interactive labels and ref IDs for point-and-click actions.
  • Remote browsers — can connect to remote CDP endpoints (Browserless, Browserbase, or any cdpUrl).
  • Sandbox sessions — browser access can be denied for non-main sessions (security).
  • SSRF policy — configurable private network access (dangerouslyAllowPrivateNetwork).

Layer 11: Device Nodes (Companion Apps)

Nodes are physical devices that extend the agent's reach into the real world. Your iPhone can be a "node" — the agent can ask it to take a photo, record your screen, get your GPS location, or send a notification. Your Mac can also be a node for running commands or accessing the webcam. Devices connect to the Gateway over WebSocket and authenticate via a pairing process (like Bluetooth pairing — you approve the device once).

Layer 12: Web UI & Canvas

OpenClaw has a built-in web interface served directly from the Gateway. The Control UI is a dashboard where you can monitor sessions, check health, manage config, and see what the agent is doing. WebChat is a chat interface in your browser. Canvas is a special visual workspace where the agent can push interactive HTML content — like dashboards, data visualizations, or custom interfaces. Think of Canvas as a screen that the AI can draw on in real-time.

Layer 13: Configuration System

Everything in OpenClaw is controlled by a single config file: ~/.openclaw/openclaw.json. It's like the control panel of a spaceship — one place to configure which AI model to use, which messaging apps to connect, who's allowed to talk to the agent, what scheduled tasks to run, and more. The config supports environment variable substitution (so secrets aren't hardcoded), hot-reload (changes take effect immediately), and strict validation (typos are caught before they cause problems).

  • Format — JSON5 (allows comments, trailing commas).
  • Environment variables — ${VAR_NAME} syntax, loaded from ~/.openclaw/.env.
  • Hot reload modes — watch (inotify/FSEvents), poll (periodic), hybrid (watch + poll fallback).
  • Strict validation — TypeBox schemas validate every key. Unknown keys cause startup warnings.
  • Config RPC — config.get, config.patch methods over WebSocket for programmatic updates.
  • Config splitting — can split config across multiple files with includes.
  • Secret refs — reference secrets from files: ${file:~/.openclaw/credentials/token}.

Layer 14: Security Model

OpenClaw takes security seriously because it has access to your messages, files, and devices. By default, unknown people can't talk to your agent (they get a pairing code instead). The Gateway only listens on localhost (can't be reached from the internet). API keys are stored in protected files. In group chats, the agent can be sandboxed (runs commands inside Docker containers). There's a "dangerous tools" classification system — some tools need extra approval. And there are strict rules about what the agent can and can't do in different contexts.

  • DM pairing — default for unknown senders. Pairing code must be approved via CLI before the bot responds.
  • Loopback binding — Gateway binds to 127.0.0.1 by default. Remote access only via Tailscale Serve/Funnel or SSH tunnels.
  • Sandboxing — non-main sessions can run inside per-session Docker containers. Tool allowlist/denylist configurable.
  • Tool classification — dangerous-tools.js classifies tools by risk level. Browser, canvas, nodes, cron, gateway tools are denied in sandbox mode.
  • Auth token rotation — Gateway tokens, channel tokens, and model API keys all support rotation.
  • Secret storage — credentials in ~/.openclaw/credentials/ with chmod 600. Never committed to git.
  • SSRF protection — fetch tool blocks private network access by default.
  • Send policies — rules can prevent the agent from sending messages to specific channels, chat types, or session key patterns.

OpenClaw is not a simple chatbot wrapper. With 625 compiled modules, 44 extensions, 52 skills, and 14 core subsystems, it's a full-fledged personal AI operating system. It handles everything from WebSocket protocol management to APNS push notifications, from cron scheduling to Docker sandboxing, from WhatsApp QR login to OpenTelemetry diagnostics. The architecture is designed around a single control plane (the Gateway) with a plugin-based extension system that keeps the core clean while supporting an enormous surface area of integrations.
